# ADR 001: Technology Stack Selection

## Status
Accepted

## Context
Need to select technology stack for NetWatch network threat detection platform.

## Decision
- **Frontend**: React 18 + TypeScript 5 + Vite 5 + Tailwind CSS 4
- **Backend**: Python 3.12 + FastAPI 0.104 + Pydantic 2 + SQLAlchemy 2
- **Database**: PostgreSQL 16 with psycopg3 (async)
- **Testing**: pytest + pytest-asyncio (backend), Vitest (frontend)
- **Linting**: Ruff + Black + mypy (backend), ESLint + Prettier (frontend)

## Consequences
- **Positive**: Modern, performant, type-safe, good ecosystem
- **Negative**: Learning curve for team unfamiliar with stack
- **Risks**: Tailwind v4 breaking changes, FastAPI migration path

## Alternatives Considered
- Next.js (overkill for dashboard)
- Django (heavier than needed)
- Express.js (less type safety)
- GraphQL (unnecessary complexity)

# ADR 002: Detection Engine Architecture

## Status
Accepted

## Context
Design rule-based detection engine for VPC Flow Log analysis.

## Decision
- Plugin-based rule architecture with `DetectionRule` base class
- Each rule implements `match(entry) -> Optional[DetectionResult]`
- `DetectionEngine` orchestrates all rules
- Rules are stateless (except PortScan/BruteForce which track state)

## Consequences
- **Positive**: Extensible, testable, simple mental model
- **Negative**: Stateful rules need careful reset handling
- **Risks**: Memory growth in long-running processes

## Alternatives Considered
- SQL-based detection (less flexible)
- ML-based (requires training data)
- Stream processing (overkill for MVP)

# ADR 003: Flow Log Parser Design

## Status
Accepted

## Context
Parse AWS VPC Flow Logs in multiple formats.

## Decision
- Single `FlowLogParser` class with format detection by extension
- Streaming parser for JSONL/GZIP to handle large files
- `ParseResult` with detailed error reporting
- Validation against required schema fields

## Consequences
- **Positive**: Memory efficient, detailed errors, format agnostic
- **Negative**: More code than single-format parser
- **Risks**: GZIP decompression memory for huge files

## Alternatives Considered
- Separate parser per format
- Pandas-based parsing
- AWS Glue (external dependency)

# ADR 004: Security Group Analyzer

## Status
Accepted

## Context
Analyze AWS Security Groups for common misconfigurations.

## Decision
- Rule-based analyzer similar to detection engine
- Focus on 0.0.0.0/0 and ::/0 exposure
- 8 built-in rules covering common ports
- Structured findings with remediation guidance

## Consequences
- **Positive**: Comprehensive coverage, actionable output
- **Negative**: IPv6 rules need more testing
- **Risks**: False positives for legitimate public services

## Alternatives Considered
- AWS Config rules (managed service)
- CloudFormation drift detection
- Manual review (not scalable)

# ADR 005: API Design

## Status
Accepted

## Context
Design REST API for NetWatch services.

## Decision
- RESTful with OpenAPI 3.1 specification
- Versioned under `/api/v1/`
- Consistent error format with RFC 7807
- Pydantic models for request/response validation

## Consequences
- **Positive**: Standard, well-documented, type-safe
- **Negative**: More boilerplate than RPC
- **Risks**: Versioning complexity as API evolves

## Alternatives Considered
- GraphQL (overkill)
- gRPC (not browser-friendly)
- tRPC (tight coupling)

# ADR 006: Project Structure

## Status
Accepted

## Context
Organize codebase for maintainability and separation of concerns.

## Decision
- Monorepo with separate packages: frontend, backend, detection, ingestion, security_audit
- Shared types via Python packages
- Independent testability
- Clear module boundaries

## Consequences
- **Positive**: Clear ownership, independent deployment, reusable components
- **Negative**: More complex than single package
- **Risks**: Circular dependency temptation

## Alternatives Considered
- Single Python package
- Separate repositories
- Microservices from day one
